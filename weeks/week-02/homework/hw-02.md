# Bài Tập 2: Audit Public API Thực Tế — GitHub REST API

> **Học phần**: Kiến trúc hướng dịch vụ (SOA) — Tuần 02  
> **Đối tượng Audit**: **GitHub REST API** (Phiên bản chuẩn hóa `X-GitHub-Api-Version: 2022-11-28`)  
> **Base URL**: `https://api.github.com`  
> **Tài liệu tham chiếu chính thức**: [GitHub REST API Documentation](https://docs.github.com/en/rest)

---

## 1. Tổng Quan Về GitHub REST API

GitHub REST API là một trong những API công cộng quy mô lớn nhất thế giới, phục vụ hàng tỷ lượt gọi mỗi ngày từ các lập trình viên, hệ thống CI/CD, và ứng dụng bên thứ ba. Hệ thống tuân thủ chặt chẽ các quy chuẩn của giao thức HTTP/1.1 và các nguyên lý kiến trúc hướng tài nguyên (Resource-Oriented Architecture - ROA).

- **Định dạng dữ liệu**: `application/vnd.github+json` (Custom Vendor Media Type).
- **Cơ chế xác thực**: Stateless thông qua `Authorization: Bearer <token>` hoặc Fine-grained Personal Access Tokens.
- **Chiến lược phân phiên bản**: Khai báo tường minh qua header `X-GitHub-Api-Version: 2022-11-28`.

## 3. Phân Tích Kỹ Thuật Chi Tiết Từng Endpoint

### Endpoint 1: Lấy thông tin người dùng công khai
`GET /users/{username}`
- **Nguồn tài liệu**: [docs.github.com/en/rest/users/users#get-a-user](https://docs.github.com/en/rest/users/users#get-a-user)
- **Mục đích**: Truy vấn thông tin hồ sơ của một tài khoản GitHub cụ thể.
- **HTTP Method**: `GET` — Thao tác chỉ đọc (**Safe = True**, **Idempotent = True** theo RFC 9110 §9.2).
- **Request Headers**:
  - `Accept: application/vnd.github+json` (Yêu cầu định dạng biểu diễn).
  - `If-None-Match: "<ETag>"` (Tùy chọn: Dùng cho Conditional Request).
- **Response Headers**:
  - `Content-Type: application/json; charset=utf-8`
  - `ETag: W/"..."` (Dùng để cache và kiểm tra phiên bản dữ liệu).
  - `Cache-Control: public, max-age=60, s-maxage=60`
  - `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`
- **Mã trạng thái (Status Codes)**:
  - `200 OK`: Thành công, trả về JSON hồ sơ người dùng.
  - `304 Not Modified`: Dữ liệu chưa bị thay đổi so với giá trị `ETag` gửi lên; không tốn hạn mức rate-limit chính.
  - `404 Not Found`: Không tìm thấy `username` tương ứng.
- **Đánh giá RESTful**: **Hoàn toàn tuân thủ**. URI sử dụng danh từ số nhiều `/users` kết hợp định danh tài nguyên `{username}`. Hỗ trợ đầy đủ Caching và Conditional Requests.

---

### Endpoint 2: Lấy danh sách Issues của một Repository
`GET /repos/{owner}/{repo}/issues`
- **Nguồn tài liệu**: [docs.github.com/en/rest/issues/issues#list-repository-issues](https://docs.github.com/en/rest/issues/issues#list-repository-issues)
- **Mục đích**: Lấy danh sách các issue/pull request trong repository (hỗ trợ lọc theo `state`, `labels`, `sort`).
- **HTTP Method**: `GET` (**Safe = True**, **Idempotent = True**).
- **Request Headers**:
  - `Accept: application/vnd.github+json`
  - `X-GitHub-Api-Version: 2022-11-28`
- **Response Headers**:
  - `Link: <https://api.github.com/...?page=2>; rel="next", <...>; rel="last"` (RFC 5988 Web Linking cho phân trang).
  - `ETag: W/"..."`
- **Mã trạng thái (Status Codes)**:
  - `200 OK`: Trả về mảng JSON chứa các issue thỏa điều kiện.
  - `301 Moved Permanently`: Repository đã đổi tên hoặc chuyển quyền sở hữu (kèm header `Location`).
  - `304 Not Modified`: Cache còn hiệu lực.
  - `404 Not Found`: Repository không tồn tại hoặc ở chế độ private mà token không đủ quyền.
- **Đánh giá RESTful**: **Xuất sắc**. Cấu trúc URI phân cấp tự nhiên (`repos/{owner}/{repo}/issues`). Đặc biệt, việc sử dụng header `Link` với các quan hệ liên kết `rel="next"`, `rel="prev"` phản ánh chính xác tư tưởng Hypermedia của REST.

---

### Endpoint 3: Tạo mới một Issue
`POST /repos/{owner}/{repo}/issues`
- **Nguồn tài liệu**: [docs.github.com/en/rest/issues/issues#create-an-issue](https://docs.github.com/en/rest/issues/issues#create-an-issue)
- **Mục đích**: Mở một issue mới trong repository.
- **HTTP Method**: `POST` (**Safe = False**, **Idempotent = False** — mỗi lần gọi thành công tạo một issue mới với số ID tự tăng).
- **Request Headers & Body**:
  - `Authorization: Bearer <token>` (Bắt buộc quyền ghi `issues: write`).
  - `Content-Type: application/json`
  - Body: `{"title": "Bug in auth module", "body": "Steps to reproduce...", "labels": ["bug"]}`
- **Response Headers**:
  - `Location: https://api.github.com/repos/{owner}/{repo}/issues/{issue_number}`
  - `Content-Type: application/json; charset=utf-8`
- **Mã trạng thái (Status Codes)**:
  - `201 Created`: Tạo issue thành công; trả kèm header `Location` trỏ tới URI của issue mới tạo.
  - `400 Bad Request`: Payload JSON gửi lên sai cú pháp (malformed).
  - `403 Forbidden`: Tài khoản bị khóa, vi phạm spam detection, hoặc token không đủ quyền ghi.
  - `404 Not Found`: Không tìm thấy repository.
  - `422 Unprocessable Entity`: Dữ liệu JSON đúng cú pháp nhưng vi phạm quy tắc nghiệp vụ (ví dụ: thiếu trường bắt buộc `title` hoặc nhãn `labels` không hợp lệ).
- **Đánh giá RESTful**: **Hoàn toàn chuẩn mực**. Sử dụng đúng mã `201 Created` kết hợp header `Location`, phân định rõ ràng giữa `400` (lỗi cú pháp) và `422` (lỗi validation nghiệp vụ).

---

### Endpoint 4: Cập nhật từng phần một Issue
`PATCH /repos/{owner}/{repo}/issues/{issue_number}`
- **Nguồn tài liệu**: [docs.github.com/en/rest/issues/issues#update-an-issue](https://docs.github.com/en/rest/issues/issues#update-an-issue)
- **Mục đích**: Chỉnh sửa tiêu đề, nội dung, người được gán, hoặc đóng/mở lại một issue (`state: "closed"`).
- **HTTP Method**: `PATCH` (**Safe = False**, **Idempotent = Tùy thuộc thao tác** — Chuẩn RFC 5789 cho cập nhật từng phần).
- **Request Headers & Body**:
  - `Authorization: Bearer <token>`
  - `Content-Type: application/json`
  - Body: Chỉ gửi các trường cần cập nhật, ví dụ `{"state": "closed", "state_reason": "completed"}`.
- **Response Headers**:
  - `Content-Type: application/json; charset=utf-8`
- **Mã trạng thái (Status Codes)**:
  - `200 OK`: Cập nhật thành công, trả về toàn bộ representation mới nhất của issue.
  - `301 Moved Permanently`: Repository đã chuyển đổi URI.
  - `403 Forbidden`: Người dùng không có quyền chỉnh sửa issue này.
  - `404 Not Found`: Issue hoặc repository không tồn tại.
  - `422 Unprocessable Entity`: Giá trị trường không hợp lệ (ví dụ `state` truyền chuỗi không phải `"open"` hoặc `"closed"`).
  - `503 Service Unavailable`: Dịch vụ tạm thời gặp sự cố do phụ thuộc hạ tầng lưu trữ.
- **Đánh giá RESTful**: **Chuẩn mực theo RFC 5789**. GitHub sử dụng đúng phương thức `PATCH` cho cập nhật từng phần thay vì lạm dụng `PUT` (vốn đòi hỏi thay thế toàn bộ bản ghi).

---

### Endpoint 5: Hủy đánh dấu sao một Repository (Unstar)
`DELETE /user/starred/{owner}/{repo}`
- **Nguồn tài liệu**: [docs.github.com/en/rest/activity/starring#unstar-a-repository-for-the-authenticated-user](https://docs.github.com/en/rest/activity/starring#unstar-a-repository-for-the-authenticated-user)
- **Mục đích**: Xóa bỏ trạng thái "đã gắn sao" (Star) của người dùng hiện tại đối với một repository.
- **HTTP Method**: `DELETE` (**Safe = False**, **Idempotent = True** — gọi 1 lần hay 100 lần thì kết quả cuối cùng là repo vẫn không còn được người dùng đó gắn sao).
- **Request Headers**:
  - `Authorization: Bearer <token>` (Yêu cầu quyền ghi `starring`).
  - `Accept: application/vnd.github+json`
- **Response Headers**:
  - `X-RateLimit-Limit`, `X-RateLimit-Remaining`
- **Mã trạng thái (Status Codes)**:
  - `204 No Content`: Hủy gắn sao thành công; **không trả body**.
  - `304 Not Modified`: Trạng thái không đổi.
  - `401 Unauthorized`: Chưa đăng nhập hoặc token sai.
  - `403 Forbidden`: Token không đủ quyền hạn.
  - `404 Not Found`: Repository không tồn tại.
- **Đánh giá RESTful**: **Chuẩn mực**. Mô hình hóa hành động "bỏ gắn sao" thành thao tác `DELETE` trên tài nguyên quan hệ (Association Resource) `/user/starred/{owner}/{repo}`. Trả về đúng mã trạng thái `204 No Content` khi xử lý hoàn tất mà không cần body.

## 4. Đánh Giá Toàn Diện Tính RESTful Của GitHub API

Đối chiếu với **6 ràng buộc kiến trúc của Roy Fielding** và **Mô hình trưởng thành Richardson (RMM)**:

### 1. Đối chiếu 6 Ràng buộc Kiến trúc (Roy Fielding 2000)
1. **Client-Server**: **ĐẠT**. Tách biệt triệt để tầng giao diện (Web, GitHub Desktop, GitHub CLI) và tầng dữ liệu thông qua định dạng JSON chuẩn.
2. **Stateless**: **ĐẠT**. Server không duy trì session state giữa các request. Mỗi request tự mang đầy đủ ngữ cảnh xác thực qua Bearer Token.
3. **Cacheable**: **ĐẠT**. Hỗ trợ mạnh mẽ `ETag`, `Cache-Control`, và Conditional Requests (`If-None-Match` trả về `304 Not Modified`) giúp tiết kiệm băng thông và tối ưu hạn mức rate-limit.
4. **Layered System**: **ĐẠT**. Hệ thống triển khai qua nhiều tầng trung gian độc lập: Fastly CDN, DDoS Shield, API Gateway định tuyến và cân bằng tải.
5. **Code on Demand**: **BỎ QUA** (Theo đúng đặc thù REST API hiện đại, chỉ truyền tải dữ liệu JSON, không gửi script thực thi).
6. **Uniform Interface**:
   - *Resource Identification*: **ĐẠT**. Đặt tên bằng danh từ số nhiều, cấu trúc URI phân cấp chặt chẽ (`/repos/{owner}/{repo}/issues`).
   - *Manipulation through Representations*: **ĐẠT**. Thao tác qua biểu diễn JSON, áp dụng chuẩn xác `PATCH` (RFC 5789) và `PUT`.
   - *Self-descriptive Messages*: **ĐẠT**. Sử dụng Custom Media Type `application/vnd.github+json` và mã trạng thái HTTP chuẩn mực.
   - *HATEOAS*: **ĐẠT MỘT PHẦN (Partial HATEOAS)**. GitHub cung cấp header `Link` cho phân trang và nhúng các trường URL (`comments_url`, `events_url`) vào body JSON. Tuy nhiên, GitHub không sử dụng một chuẩn Hypermedia đầy đủ (như HAL, Siren, JSON:API) để dẫn dắt state-machine ứng dụng tự động.

### 2. Định vị trên Mô hình Trưởng Thành Richardson (RMM)
- **Cấp độ đạt được**: **Level 2 (Vững chắc) + Level 3 (Một phần)**.
- **Kết luận**: GitHub REST API là một trong những hình mẫu tiêu biểu nhất của thiết kế **Resource-Oriented API** trong công nghiệp thực tế. Đúng như phân tích trong slide bài giảng: Việc chưa đạt 100% HATEOAS thuần túy là một **đánh đổi có chủ đích (Pragmatic Trade-off)** để giảm chi phí băng thông và đơn giản hóa việc tích hợp cho SDK/Client, chứ không làm suy giảm chất lượng kiến trúc của hệ thống.
